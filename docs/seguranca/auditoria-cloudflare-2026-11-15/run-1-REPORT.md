## 2. Security posture

The authorization core is strong in source: every SECURITY DEFINER function still executable by `authenticated` was found to carry a role and unit guard, `hermes_*` grants stay revoked, and the AI paths de-identify and fail closed. The open leads sit at the edges of that core: how a second factor is obtained or reset (TOTP enrollment at aal1, cross-tenant reset through a unilateral vínculo), how an account joins a unit (invite codes without an attempt limit), what an integrator IP allowlist trusts (leftmost X-Forwarded-For), what the print pipeline renders (one unescaped stored field), and what the `atendimento` bucket lets a unit member overwrite. None could be executed here; each needs a homologation check before it is called a vulnerability.

## 3. Confirmed findings

None. No candidate could be executed under the required sandbox, so none meets the confirmed contract.

## 5. Hardening notes (not findings)

- biblioteca/app/main.py:73 compares the bearer key with != on a publicly routed service (hermes/deploy/Caddyfile:16-27); use hmac.compare_digest. /health (main.py:324-330) is unauthenticated and discloses chunk count and model name.
- supabase/functions/clinical-search/index.ts:46 loads at most 20000 active patient names for pseudonymisation; in search mode, without NER, names beyond that limit leave only regex-masked (search mode reaches only the local embedder, not the external model).
- hermes/src/server/skill-api.ts:379-381 still trusts the subject (wa_id or canal+identificador) from the request body behind one shared token; the plugin binds it from the session, but any holder of HERMES_SKILL_TOKEN with a shell (legacy hermes/deploy/nous-skill/*.sh with CORUJA_WA_ID) can impersonate any linked user. Retire the shell skills and remove the wa_id body path, or issue per-session opaque tokens as the file comment proposes.
- hermes/src/agent/tools.ts:85-89: liberar_quarentena relies on a system-prompt instruction for confirmation; no consumer of the liberado flag exists today, so there is no impact, but any future consumer needs a deterministic confirmation bound to the item id.
- Telegram link codes (supabase/migrations/20261020000002_hermes_grant_vincular.sql:73-93) are rate-limited only per identifier in per-process memory (hermes/src/server/skill-api.ts:534-539, hermes/deploy/nous-plugin/chefe-coruja/consulta.py:669-673); add a global or per-code attempt limit in the database.
- hermes/src/server/skill-api.ts:449 evaluates autorizado() on the principal unit's role before swapping to the requested unit; current handlers and RPCs re-check, but re-running autorizado() after the swap would remove the dependency on each RPC.
- supabase/functions/_shared/folhas.ts cabecalho(): escape doc and sub at the sink and remove the pre-escaping in receita/pedidoExames/relClassificacao, so new callers cannot reintroduce raw HTML. relPareceres (folhas.ts:1127) also passes especialidade/status raw. It is safe today only because especialidade has an FK to a seeded list and status has a CHECK.
- Print windows (src/lib/prontuario.ts:160,222,261; ImpressaoProntuario.tsx:271; Alta.tsx; pulseira.ts) keep window.opener. Set janela.opener = null after writing, or add Cross-Origin-Opener-Policy, to remove reverse-tabnabbing reach from any future markup injection.
- banners.link_url (20260815000008_fase1_banners.sql:13) has no server-side scheme CHECK. Add CHECK (link_url ~ '^https://'), matching imagem_url, so a direct PostgREST write cannot store javascript:/data: URLs that React 19 and CSP currently neutralise.
- folha edge function sends Access-Control-Allow-Origin '*' with bearer-token auth. This is not exploitable without the token, but it could be narrowed to the app origins.
- Drop atendimento_update or narrow it to super admin (mirroring atendimento_delete); add a sha256 column to anexos_prontuario that registrar_anexo_prontuario fills from storage.objects metadata, so a byte swap is detectable.
- Bucket 'banners' is public with no allowed_mime_types or file_size_limit (20260815000008:101-103); gestor uploads of SVG/HTML would be served from the Supabase storage origin. Set allowed_mime_types to image/png, image/jpeg, image/webp and a size limit, as already done for 'painel'.
- Buckets 'atendimento' and 'farmacia' have no allowed_mime_types; registrar_anexo_prontuario and registrar_arquivo_farmacia check only the client-declared MIME/extension, not the stored object's content type. Add bucket-level MIME allow-lists.
- Buckets 'fotos' (private, used with upsert:true and getPublicUrl in src/pages/Perfil.tsx:161-170) and 'receitas' have no storage.objects policies in source; any policies that exist were created outside migrations and cannot be reviewed. Codify them in a migration.
- Edge functions import @supabase/supabase-js@2 (major range) from esm.sh in api, webhooks and folha and via npm: in the others, with no deno.lock. Pin an exact version, prefer npm: over esm.sh, and commit a deno.lock, because these functions hold the service-role key.
- CI actions are tag-pinned (actions/checkout@v4, setup-node@v4, cache@v4, setup-python@v5, supabase/setup-cli@v1), Supabase images are pulled by tag from docker.io/public.ecr.aws/ghcr.io without the digest the comments mention, and 'pip install tzdata' is unpinned. No secret or release is exposed today; pin actions to SHAs and images to digests before any secret or deploy step is added.
- biblioteca/app/requirements.txt uses floating ranges without --require-hashes, and the Dockerfiles use tag-only base images (python:3.12-slim, node:22-alpine, node:24-alpine, postgres:17-alpine). Pin versions and digests.
- api_fhir_pode_anexar (20261211000001_api_imagem.sql:377-384) checks key, exam scope and unit but not the IP list or the rate limit, so a valid key from a non-allowlisted IP still makes the Edge Function upload up to ~10 MB to bucket exames before api_v1_fhir returns 403 and the object is removed (index.ts:180-199). Reuse the IP/limit checks or move the check into one RPC.
- Body size limits in the api function (index.ts:93 64 KB, index.ts:164 15 MB) rely on the Content-Length header; a chunked request without it passes the check and req.json() reads the whole body. Availability not tested in this run; enforce the limit while reading the stream.
- Rate limit in all api_v1* ports is count-then-insert without a lock (e.g. 20261104000002_api_integradores.sql:285-291), so concurrent requests can exceed limite_por_minuto slightly.
- api_acessos_da_chave and api_chaves_lista (20261104000002_api_integradores.sql:116-199) and webhook_destinos_lista show a multi-unit key's or destination's other units, access log entries (unit name, IP, status) and lets a gestor of any one unit revoke a key or switch off a destination serving other units; documented design, but it is cross-unit metadata and availability control.
- Webhook SSRF guard is hostname-only (assinatura.ts:43-53, 20270201000001_webhooks.sql:54-59): a public DNS name resolving to a private or link-local address passes. Only super_admin (with 2FA) can set the URL; consider resolving and rejecting private ranges before fetch, since the Edge runtime egress network is outside the application's trust model.
- x-coruja-borda (contrato.ts:157) and webhook_motor_autorizado (20270201000002_webhooks_motor.sql:165) compare secrets with ordinary equality; remote timing exploitation is impractical, but a constant-time compare is cheap.
- The api_chaves.ambiente value (live/test) is never enforced by the ports; a cc_test_ key created in the production database has full production access. Fine if intended, but the label suggests otherwise.
- The same leftmost X-Forwarded-For pattern is used by pedir-demonstracao (supabase/functions/pedir-demonstracao/regras.test.ts:58); that unit is peer-owned and was not investigated here.
- registrar_erro_cliente (supabase/migrations/20261018000001_correcoes_pentest.sql:85-105): both anti-flood caps are skipped for anon callers when private.requisicao_ip() returns NULL (malformed or absent x-forwarded-for) and are rotatable by changing the header; key the cap on a header-independent global window as done for primeiro_acesso_bloqueado. Volume/availability only.
- Contract codes CT-YYYY-NNN (supabase/migrations/20261003000001_convites_primeiro_acesso.sql:138) give 1000 values per year; conferir_contrato under the 120/5min global breaker can enumerate a year in under an hour, revealing organization name, unit count and default role, and the signUp path can create pending adesoes (no privilege until an admin acts). Use random, longer contract codes or require dominio_email.
- private.origem_requisicao and private.requisicao_ip trust the first x-forwarded-for element (client-controlled); per-origin limits are bypassable and a third party's IP can be placed in the header to lock that origin out. Prefer the gateway-appended (last trusted) hop.
- The global first-access breaker (120 failures/5 min) can be tripped by any anonymous caller to block legitimate onboarding for everyone; availability only.
- landing/app/api/contato/route.ts has no Turnstile or rate limit (unlike pedir-demonstracao); recipient is fixed so impact is inbox spam and Resend quota consumption.
- conferir_convite and pedir_novo_convite return the inviter's full name for valid or expired codes (20261003000001:430,463); by design but worth keeping minimal.
- The hermes_* EXECUTE revocation is a one-time DO loop (supabase/migrations/20261022000002_fix_2fa_email_hermes_grants.sql:105-115) and Supabase default privileges still grant EXECUTE on new public functions to authenticated (only PUBLIC/anon are removed by 20260926000001:18). Any future hermes_* function (or DROP+CREATE of an existing one) is authenticated-callable unless its migration repeats the REVOKE. supabase/tests/porte_redteam_v1_hermes.sql checks table grants for hermes_user but not EXECUTE for authenticated; add a CI assertion that has_function_privilege('authenticated', oid, 'EXECUTE') is false for every public function named hermes_% (and every function that takes p_perfil as subject identity), or add ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM authenticated and grant per function.
- hermes_user and hermes_job are granted to authenticator (supabase/migrations/20261020000001_hermes_least_privilege.sql:40-41) although the Hermes server now connects through dedicated LOGIN roles (20261022000007). Keeping them under authenticator makes the signing key the only barrier to a PostgREST session as hermes_user; revoking that membership once the cutover is complete removes the path.
- private.papel_na_unidade returns only the strongest role, so guards written as papel_na_unidade(u) = 'gestor' deny a user who is also 'admin' in that unit; this is a false-deny only, but new guards should use tenho_papel or gestor_da_unidade consistently.
- herdar_segundo_fator (20261022000011:24-34) accepts any previous session_id of the same user with a sessao_ok row under 24 h without checking that the session still exists in auth.sessions. A signed-out or revoked session can be inherited by anyone who has the password plus an old access token or session_id. Bind it to an existing auth.sessions row, or to a per-session secret held only by the browser.
- Two SECURITY DEFINER views (vw_censo_unidade, vw_indicadores_unidade) are readable by GET before 2FA because portao_requisicao lets table GETs through and the views bypass RLS. They return only aggregates with 1-4 suppression, so no patient identity is exposed. Adding PERFORM private.exigir_segundo_fator() to fn_censo_unidade/fn_indicadores_unidade would make the gate uniform.
- The whole server-side gate depends on configuracao_plataforma.exigir_segundo_fator, which defaults to false (20260926000009:31-33). The production value is not in source; with it off, none of these controls apply.
- Email OTP brute-force bound is about 25 guesses per hour per account (5 codes/hour times 5 tries each, 6 digits). This is acceptable but has no account-level daily cap or alerting. Consider a rolling daily limit on solicitar_codigo_2fa.
- enviar-codigo-2fa defaults Access-Control-Allow-Origin to '*' when APP_ORIGIN is unset (index.ts:17). The call needs a bearer token, so this is not exploitable as CSRF. comCors overrides it per request.
